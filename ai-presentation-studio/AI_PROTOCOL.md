# AI 雙人接力開發協議

這份協議適用於所有參與本專案的 AI，不分平台。

Claude 要遵守。GPT 要遵守。之後換成任何 AI 也要遵守。

讀完這份協議，才可以開始工作。

---

## 零、你的身分

你不是一個孤立工作的 AI。

你是兩人開發團隊的其中一員。另一位是不同平台的 AI。

你的輸出不只服務目前的使用者，也必須服務下一個接手的 AI。

離開專案前，要讓下一個 AI 做得到這件事：

> 我知道上一個 AI 做了什麼、為什麼這樣做、現在做到哪裡、我下一步該做什麼。

---

## 一、紀錄放在專案裡，不放在聊天室

所有接力紀錄存在專案資料夾內。

不可以依賴 AI 平台本身的聊天紀錄。使用者換平台、清空對話、開新視窗，紀錄都必須還在。

位置固定如下：

```
ai-presentation-studio/
├── AI_PROTOCOL.md          本協議（規則）
├── AI_HANDOFF.md           目前最新接力狀態（短）
└── AI_HISTORY/             歷次 Session 紀錄（長）
    ├── 2026-09-02_001_Claude.md
    ├── 2026-09-03_002_GPT.md
    └── ...
```

Session 檔名格式固定：

```
日期_流水號_AI名稱.md
```

流水號必須遞增，不可重複，不可跳號。

---

## 二、開始工作前，先做接力檢查

不要直接開始工作。

不要先改程式碼。不要先跑指令。不要先問問題。

先做這六步：

1. 讀 `AI_PROTOCOL.md`（本檔）
2. 讀 `AI_HANDOFF.md`
3. 找出最新一筆 Session
4. 判斷最新一次工作是哪一個 AI 完成的
5. 確認自己是哪一個 AI
6. 依第三條決定要讀哪些紀錄

---

## 三、要讀哪些紀錄

### 情況 A：最新 Session 是另一個 AI

從**自己上一個 Session** 開始，依序讀到**最新 Session**。

例：

```
001_Claude
002_GPT
003_Claude
004_GPT    ← 最新
```

現在是 Claude。至少要讀 `003_Claude` 與 `004_GPT`。

不可以只讀 `004_GPT`。你自己上一輪留下的上下文在 `003_Claude` 裡面。

### 情況 B：最新 Session 是自己

直接從最新那一筆繼續。

不需要重讀全部歷史。必要時才回頭追溯。

### 情況 C：第一次使用這個專案

`AI_HISTORY/` 不存在或是空的，就先建立紀錄系統。

然後檢查：專案結構、README、`CLAUDE.md` / `AGENTS.md` 等 AI 指示檔、Git 狀態、實際程式碼。

第一次工作不需要假設之前存在任何 AI 對話。

---

## 四、不要無腦讀完整個歷史

不要每次啟動就讀 `AI_HISTORY/` 全部檔案。那會浪費大量 token。

正常範圍：

```
自己的最後一次 Session
        ↓
      之後所有 Session
        ↓
      最新 Session
```

只有當目前工作真的需要更早的背景，才往前追溯。

---

## 五、紀錄以實際專案狀態為準

不要因為看到 `004_GPT.md` 就假設 GPT 真的做完了那些事。

必要時自己查：

```bash
git status
git log --oneline
git diff
npm test
```

紀錄與實際程式碼不一致時：

以**實際程式碼**為準，並在新的 Session 紀錄中明確指出不一致。

---

## 六、不要覆蓋另一個 AI 的工作

兩個 AI 是合作關係，不是互相搶程式碼。

發現另一個 AI 已經完成某個功能：

不要重新實作。先理解它的設計。

只有下列三種情況才可以改：

1. 發現 Bug
2. 發現設計問題（要在紀錄中說明理由）
3. 使用者要求修改

否則保留既有成果。

---

## 七、每次工作結束都要留紀錄

每一次對話工作完成、準備交棒時，都要建立新的 Session 紀錄。

不要等專案完成才紀錄。

即使只改了一個小功能，也要留紀錄。

### Session 紀錄格式

```markdown
# Session <流水號>

- AI：
- 日期：
- Session：
- 工作狀態：進行中 / 完成 / 阻塞
- Git Commit：

## 1. 本次任務
使用者要求做什麼。

## 2. 實際完成
實際完成了什麼。

## 3. 修改的檔案
新增 / 修改 / 刪除，分開列。

## 4. 技術決策
做了什麼決定，為什麼。
影響未來開發的，標上「⚠️ 已確定的設計決策」。

## 5. 問題與解決方式
遇到的重要問題，怎麼解的。

## 6. 尚未完成
明確列出還沒做完的事。

## 7. 下一個 AI 必須知道
最重要的區塊。要寫：
- 現在做到哪裡
- 下一步應該做什麼
- 有哪些東西不要亂改
- 有哪些已知問題
- 哪些決策已經確定
- 哪些地方要特別注意

## 8. 驗證結果
跑過哪些測試、結果如何、是否仍有已知錯誤。
```

---

## 八、Session 紀錄不是逐字稿

不要把整段聊天複製進去。

不要貼大量 terminal 輸出。

不要保存閒聊、重複內容、無關的來回。

只寫對下一個 AI 有價值的東西：

做了什麼、為什麼這樣做、改了什麼、哪些方案被否決、哪些問題沒解決、下一步做什麼。

---

## 九、重要決策必須寫死

會影響未來開發的決策，一定要寫進 Session 紀錄。

不可以只寫結果，要寫理由。

錯誤示範：

> 今天完成資料庫。

正確示範：

> 決定使用 PostgreSQL，不用 SQLite。
> 原因：需要多使用者並行存取。

如果未來的 AI 可能因為不知道背景而推翻這個決策，要特別標記：

```markdown
### ⚠️ 已確定的設計決策

- ...
```

---

## 十、更新 AI_HANDOFF.md

每次建立新的 Session 紀錄後，都要更新 `AI_HANDOFF.md`。

它只負責保存目前最新的接力狀態，必須保持簡短。

不要把完整內容塞進去。

固定包含：

- 最新 Session（AI、編號、日期、狀態、檔名）
- 目前專案狀態（幾句話）
- 下一步
- 重要注意事項

---

## 十一、原始資料不可被摘要取代

如果拿得到原始的 Claude Code / GPT session，不要刪除或修改它。

`AI_HISTORY/` 是給兩個 AI 共享上下文用的**摘要層**，不是原始聊天紀錄。

```
AI 平台原始 Session
        ↓  完整保存
AI_HISTORY/*.md
        ↓
AI_HANDOFF.md
```

---

## 十二、本專案的特別注意事項

### 專案有兩份副本

```
ai-presentation-studio/                              ← 本體
ai-presentation-studio/.claude/worktrees/<名稱>/     ← worktree 副本
```

動手前先跑：

```bash
git worktree list
git status
```

確認自己站在哪一份、哪一個分支。

弄錯的話，你的工作會消失在另一份副本裡。

### 已確定的設計決策，不要推翻

推翻其中任何一項之前，先讀 `AI_HISTORY/2026-09-02_001_Claude.md` 第 4 節，然後問使用者。

- 第一版完全不串接任何 AI API
- Local-first / Offline-first，沒有後端、資料庫、帳號、雲端同步
- Model / Renderer / Editor 三層分離，Renderer 是純函式
- 所有 ID 穩定唯一，禁止用陣列索引定位元素
- 資料協定版本化：`ai-presentation/v1`、`ai-presentation-patch/v1`
- 匯入內容一律經過 `src/model/sanitize.ts` 白名單清理
- 交付形式是單一 HTML 檔 `dist/AI-Presentation-Studio.html`
- 開發模式與交付模式分離，`vite-plugin-singlefile` 只在正式建置載入

### 交棒前必須通過的驗證

```bash
npm test
npm run typecheck
```

兩個都要過。沒過就在 Session 紀錄中如實寫下失敗內容，不可以宣稱完成。

## 十三、完整流程

```
開始
  ↓
讀 AI_PROTOCOL.md
  ↓
讀 AI_HANDOFF.md
  ↓
確認最新 Session 是誰
  ↓
確認自己是哪個 AI
  ↓
最新 Session 是另一個 AI？
  ├─ 是 → 從自己上一個 Session 讀到最新 Session
  └─ 否 → 直接讀自己最新 Session
  ↓
檢查實際專案狀態（git status / git log / npm test）
  ↓
開始工作
  ↓
完成 / 暫停
  ↓
建立新的 AI_HISTORY Session 紀錄
  ↓
更新 AI_HANDOFF.md
  ↓
結束
```

---

## 十四、誠實條款

- 不確定就寫不確定，不編造
- 測試沒過就寫沒過，並貼出失敗內容
- 跳過的步驟要寫出來
- 使用者講錯要直接指出，不因為對方是新手就附和
- 不要為了讓紀錄好看而美化結果

下一個 AI 會相信你寫的東西。你寫錯，它就會做錯。
