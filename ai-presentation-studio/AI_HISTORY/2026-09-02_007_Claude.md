### 關鍵發現：問題不在中文字

原本的診斷說「換字型會讓每個字寬度不同」，**這對中文字是錯的**。

在瀏覽器實測「人工智慧科技趨勢報告」這一串純中文，在微軟正黑體、新細明體、
標楷體、思源黑體底下，寬度**完全相同**（100px 字級下都是 1000px）。
中文字在各家字型都是等寬的。

真正讓版面跑掉的是**英文字母、數字與百分比符號**。

以「2026 AI 科技趨勢 Q4 Report 35%」實測：

| 設定 | 最大落差 |
| --- | --- |
| 舊版（中文字型優先，英文也交給它畫） | **11.7%** |
| 新版（Arial 優先，中文才交給後面的字型） | **0%** |

新版連「完全沒有任何中文字型」的情況都是同一個寬度。

**因此不需要內嵌字型，就能解決 Windows / macOS / iOS / Linux 的跑版問題。**

## 4. 技術決策

### ⚠️ 已確定的設計決策

1. **所有字型堆疊一律以拉丁字型開頭。**
   `fonts.test.ts` 有一項測試會檢查 `FONT_CHOICES` 的每一組，違反就會失敗。
   新增字型時請照這個規則，不要把中文字型排到第一位。

2. **只提供 Windows 與 macOS 都有、尺寸一致的拉丁字型。**
   目前是 Arial、Times New Roman、Courier New。
   不要加入只有單一系統有的字型（例如 Calibri、Helvetica Neue）。

3. **編輯器介面的字型維持原樣，沒有跟著改。**
   介面字型不會被匯出，改它只是讓編輯器在這台電腦上長得不一樣，屬於多餘的改動。
   實作過程中一度改掉，發現沒有必要後改回來。`styles.css` 有註解說明。

4. **畫布與播放模式套用 `presentation.theme.fontFamily`。**
   在此之前畫布是繼承編輯器介面的字型，和匯出結果可能不同。
   現在編輯時看到的就是匯出後的樣子。

5. **這個方案不涵蓋 Android。**
   Android 沒有 Arial，會換成尺寸不同的替代字型。
   要連 Android 都完全一致，只能內嵌字型檔（會讓檔案多 50～200 KB，並多一個外部套件依賴）。
   簡報設定的說明文字已經寫明這一點，**不要把它拿掉**。

## 5. 問題與解決方式

**問題**：診斷階段講錯了原因，說成「中文字寬度不同」。

**解決**：實際量測後修正，並在回報中明講前一次講錯。
量測方法是建立隱藏的 `<span>`，套用不同 `font-family`，比較 `getBoundingClientRect().width`。

**教訓**：**跨字型、跨系統的版面問題，一律用實際量測，不要用直覺推論。**
`document.fonts.check()` 連不存在的字型都會回報 `true`，**不可以拿來判斷字型是否安裝**。
可靠的做法是「用該字型量一段字串的寬度，與通用字族的寬度比較」。

**問題**：舊存檔的字型不會自動更新。

**解決**：依 Session 006 的教訓，一開始就寫了 `migratePresentationFonts` 與對應測試。
實測載入舊 localStorage 後，主題字型確實被換成新的拉丁優先版本。
